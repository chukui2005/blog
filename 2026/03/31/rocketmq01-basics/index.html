RocketMQ基础与核心概念

核心知识点速览

知识点 要点
RocketMQ是什么 阿里开源分布式消息中间件，Java编写，十万级吞吐
核心架构 Producer → NameServer → Broker → Consumer
路由中心 NameServer无状态、可集群，Broker心跳注册
存储模型 CommitLog顺序写 + ConsumeQueue逻辑队列
消息类型 普通/顺序/延迟/事务消息
消费模式 集群消费（默认）+ 广播消费

一、RocketMQ整体架构

核心组件

组件 说明
NameServer 注册中心/路由中心，管理Broker元数据，无状态可集群
Broker 消息存储节点，主从架构，负责消息收发与持久化
Topic 主题，消息的逻辑分类
MessageQueue 消息队列，Topic下的物理分片，支持并行
Producer 消息生产者，支持事务消息
Consumer 消息消费者，集群/广播两种模式
Offset 消费位点，记录消费进度

二、NameServer：无状态路由中心

2.1 为什么不用 ZooKeeper？

特性 说明
无状态 每个NameServer独立保存全量路由，互不通信
心跳机制 Broker每30s发送心跳，NameServer每10s扫描剔除宕机节点
容错 任意NameServer挂掉不影响其他节点工作
部署 一般2～3台，与Broker同机部署节约资源

2.2 路由注册流程

三、Broker：消息存储节点

3.1 主从架构

复制方式 可靠性 吞吐 适用
同步复制 高（不丢） 低 金融、订单
异步复制 中（可能丢） 高 日志、普通业务

3.2 存储模型（高吞吐核心）

为什么快？ 所有消息共享一个CommitLog顺序写（类似Kafka），避免随机IO；ConsumeQueue只存定位信息，极小；IndexFile支持精确查询。

四、Topic与MessageQueue

4.1 Topic与队列的关系

  • MessageQueue 是消息存储与消费调度的最小单位
  • 同一Queue内消息严格FIFO，跨Queue不保证顺序
  • 读写队列数可独立配置（writeQueueNums / readQueueNums）
  • 队列数量决定并行度：一个Queue同一时刻只被一个消费者消费

4.2 发送路由策略

策略 说明
轮询（默认） 消息依次发往不同Queue，负载均衡
按Key哈希 相同业务ID → 同一Queue → 局部有序
指定队列 精确控制消息去向

五、四种消息类型

5.1 普通消息

无特殊语义，异步解耦最常用，默认3次发送重试。

5.2 顺序消息

类型 说明
全局顺序 一个Topic只有一个Queue，串行消费（吞吐低，少用）
局部顺序 按业务Key（如订单ID）路由到同一Queue，Queue内有序

电商订单场景：创建订单 → 支付 → 发货，同一订单消息必须按序消费。用 MessageQueueSelector 按订单ID取模选队列即可。

5.3 延迟消息（定时消息）

内置18个延迟级别，发送时指定延迟级别，到时间才投递给消费者：

⚠️ 只能选预设级别，不能自定义任意延迟时间（如5分37秒不支持）；更灵活的需求可用定时消息（1.9+版本支持精确时间戳）。

5.4 事务消息（半消息机制）

解决分布式事务最终一致性（本地事务 + MQ消息解耦）：

阶段 动作
发送半消息 消息对消费者不可见
执行本地事务 与半消息发送在同一事务流程
Commit/Rollback 决定消息是否投递
回查机制 兜底，保证最终一致

适用场景：下单减库存、转账+记账等跨系统事务。阿里Seata的AT/TCC模式也常与RocketMQ搭配。

六、消费机制

6.1 两种消费模式

模式 行为 适用
集群消费（默认） 一条消息只被组内一个消费者消费 任务分发、负载均衡
广播消费 每个消费者都消费所有消息 缓存刷新、配置通知

6.2 Push vs Pull

方式 说明
Push（长轮询） 客户端拉取时Broker挂起，有消息立即返回，体验接近推送
Pull 客户端主动定时拉取，灵活控制速率

RocketMQ的”Push”本质是长轮询（Long Polling），并非真正的服务端推送，兼顾实时性与实现简单。

6.3 消费进度与重试

七、RocketMQ vs Kafka vs RabbitMQ

对比维度 RocketMQ Kafka RabbitMQ
开发语言 Java Java/Scala Erlang
吞吐 十万级/s 百万级/s 万级/s
延迟 毫秒级 毫秒级 微秒级
路由能力 ✅ Tag过滤 ❌ 弱 ✅ 4种Exchange
顺序消息 ✅ 局部有序 ✅ 分区内有序 ✅ 单队列
延迟消息 ✅ 内置18级别 ❌ 不原生支持 ✅ TTL+死信
事务消息 ✅ 半消息机制 ✅ 事务API ❌
消息轨迹 ✅ 内置 需额外组件 ❌
运维复杂度 中 中（依赖ZK/KRaft） 低

选型总结

八、面试重点清单

  1. 架构：NameServer（无状态路由）+ Broker（主从存储）+ Topic/Queue
  2. 为什么不用ZK：NameServer最终一致、轻量，容忍短暂路由不一致
  3. 高吞吐：CommitLog顺序写 + ConsumeQueue定位 + IndexFile查询
  4. 顺序消息：MessageQueueSelector按业务Key路由到同一Queue
  5. 延迟消息：18个固定级别，用于订单超时等场景
  6. 事务消息：半消息 + 本地事务 + 回查，最终一致性
  7. 可靠性：同步/异步刷盘 × 同步/异步复制 四种组合
  8. 消费：集群 vs 广播、Push（长轮询）、重试队列 + 死信队列
