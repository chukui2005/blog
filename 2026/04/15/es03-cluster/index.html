知识点 要点

一、集群架构与节点角色

1.1 节点类型

节点角色 职责 配置
Master（主节点） 集群元数据管理、分片分配、索引创建/删除 node.master: true
Data（数据节点） 存储分片数据，处理读写请求 node.data: true
Ingest（预处理） 写入前管道处理（清洗、转换） node.ingest: true
Coordinating（协调） 接收请求、分发到各分片、汇总结果 默认所有节点都可充当

二、文档写入原理（近实时）

2.1 完整写入流程

2.2 关键机制

机制 说明 影响
refresh 默认1s，Buffer变Segment 频率越高实时性越好，IO开销越大
translog 写盘日志，崩溃恢复用 可配同步/异步刷盘
flush Segment落盘+清translog 产生真正持久化
merge 小段合并 减少段数，IO开销大，可调策略

面试高频：为什么ES是”近实时”？因为数据先进内存Buffer，要等 refresh（默认1s）变成 Segment 才能搜到。写入要求强实时可调 refresh: true（实时但性能差）或 refresh_interval 调小。

五、MySQL 与 ES 数据同步方案

5.1 四种方案对比

方案 原理 优点 缺点
双写 业务代码同时写MySQL和ES 简单直接 一致性难保证，耦合代码
MQ异步 写MySQL后发MQ，消费者写ES 解耦、削峰 引入MQ，最终一致
Canal/binlog 监听MySQL binlog → 同步到ES 无侵入、可靠 需部署Canal，运维成本
Logstash 定时/增量同步 生态成熟 实时性一般，全量重建慢

6.2 JVM与系统调优

项 建议
堆内存 机器内存的一半，且不超过32GB（压缩指针失效点）
禁用Swap bootstrap.memory_lock: true
文件句柄 ulimit -n 设为 65535+
磁盘 用SSD，多盘数据路径（RAID0/多路径）
段合并 大索引定期 force merge（只读索引）
冷热分离 热节点SSD + 冷节点大容量机械盘，ILM自动迁移

6.3 常见坑

七、面试重点清单

  1. 节点角色：master（元数据）/ data（存储）/ coordinating（聚合），职责分离
  2. 写入链路：Buffer → refresh(1s) → Segment可搜 → flush → merge
  3. 近实时本质：refresh 间隔决定可见延迟
  4. 读流程：Query-Then-Fetch 两阶段，深分页内存压力
  5. 脑裂：网络分区+多数派投票（N/2+1）防护
  6. 数据同步：双写/MQ/Canal/Logstash 四方案，Canal+MQ最标准
  7. 分片规划：20~40GB/分片，创建后不可改
  8. 堆内存：一半且≤32GB，禁Swap
