RocketMQ消息可靠性：不丢失方案

核心知识点速览

知识点 要点
生产端丢失 同步发送 + 失败重试（默认3次）
Broker端丢失 同步刷盘 + 同步复制（SYNC_MASTER）
消费端丢失 手动ACK + 消费重试16次 + 死信队列
重复消费 At least once语义，消费端幂等
事务消息 半消息 + 回查，保证最终一致

一、消息可能在哪个环节丢失？

三个可能丢失的环节：

  1. 生产端：网络超时、Broker未收到、发送抛异常
  2. Broker端：消息未持久化、主从都宕机（异步复制丢数据）
  3. 消费端：业务处理失败却ACK成功 / 自动提交位点

二、生产端可靠性

2.1 三种发送方式

发送方式 可靠性 吞吐 说明
同步发送（默认） 高 低 等待Broker确认才返回，失败自动重试
异步发送 中高 高 回调中处理结果，适合高吞吐
Oneway发送 低 最高 只发不确认，适合日志等可丢场景

2.3 最终兜底：本地消息表 / 事务消息

三、Broker端可靠性：刷盘 + 复制

3.1 刷盘策略

策略 行为 可靠性 吞吐
同步刷盘（SYNC_FLUSH） 写入CommitLog并落盘后才返回成功 高 低
异步刷盘（ASYNC_FLUSH） 写入PageCache即返回，后台刷盘 中（断电可能丢） 高

异步刷盘丢失窗口极短（毫秒级），且断电时依赖UPS电源保护；绝大多数场景用异步刷盘即可。

3.2 主从复制策略

复制方式 行为 可靠性
同步复制（SYNC_MASTER） Master写入并同步到Slave才返回 高（主从同时宕机才丢）
异步复制（ASYNC_MASTER） Master写入即返回，异步同步Slave 中（Master宕机未同步部分丢失）

3.3 四种组合对比

组合 可靠性 吞吐 适用场景
异步刷盘 + 异步复制 低 最高 日志、监控、可丢数据
异步刷盘 + 同步复制 中 高 普通业务消息（推荐）
同步刷盘 + 异步复制 中高 中 一般交易场景
同步刷盘 + 同步复制 最高 低 金融、对账、核心交易

面试回答模板：先讲清两个独立维度（刷盘=本机持久化，复制=主备冗余），再给出组合矩阵，最后按场景推荐。

四、消费端可靠性

4.1 消费重试机制

⚠️ 消费位点默认在消费成功后才提交（类似Kafka手动提交），处理失败不会误提交，这是消费端不丢消息的根基。

4.2 死信队列处理

操作 命令
查看死信消息 mqadmin queryMsgById -i 消息ID
重发死信 控制台”重新发送”到原Topic

4.3 消费端幂等（重复消费）

RocketMQ默认 At least once 语义：网络超时、重试、Rebalance都可能导致同一条消息被消费多次，业务必须幂等。

方案 原理 优缺点
唯一ID + 去重表 消息带全局唯一ID，DB唯一索引拦截 简单可靠，需建表
业务主键幂等 订单号/流水号做幂等键 无额外字段
Redis SETNX 消费前SETNX，已存在则跳过 高性能，注意过期时间
乐观锁 version条件更新 适合更新类操作

五、消息积压处理

排查工具 用途
控制台消息堆积图表 看积压量趋势
mqadmin consumerProgress 查消费位点落后情况
慢SQL/下游RT排查 找消费慢根因

六、面试重点清单

  1. 三环节：生产（同步发送+重试）、Broker（刷盘×复制矩阵）、消费（手动ACK+重试）
  2. 刷盘 vs 复制：一个管本机持久化，一个管主备冗余，两两组合
  3. 重试队列/死信队列：%RETRY%group、%DLQ%group，16次重试间隔递增
  4. 幂等三件套：唯一ID+去重表、业务主键、Redis SETNX
  5. 积压处理：扩消费者（上限=Queue数）、新建Topic转移、定位慢消费
  6. 事务消息：半消息+本地事务+回查（生产端最终一致性的终极方案）
