回查机制：Broker默认每60s扫描一次未决半消息，回查15次仍无结论则标记为待人工处理。业务侧通过本地事务记录表（记录事务状态）配合回查。

方式 说明

按Key查 业务Key（订单号） → IndexFile索引查询
按时间查 时间范围 + Topic → 遍历ConsumeQueue

七、性能优化要点

优化项 说明
批量发送 多条消息一批发送，减少网络往返
异步发送 高吞吐场景用异步 + 回调
异步刷盘 能接受毫秒级丢失窗口就开ASYNC_FLUSH
合理队列数 队列数 = 消费者数×2～3，够用即可
消费批量 consumeMessageBatchMaxSize 批量处理
压缩 大消息开启压缩（消息体>4KB建议）
避免大消息 超过1MB建议走OSS/DB，MQ只传引用

八、面试重点清单

  1. 事务消息四步：半消息 → 本地事务 → Commit/Rollback → 回查兜底
  2. 延迟消息原理：SCHEDULE_TOPIC_XXXX + 定时扫描，18个级别
  3. 顺序消息：按业务Key哈希选Queue + MessageListenerOrderly
  4. 过滤：Tag（简单）/ SQL92（属性表达式）
  5. 高可用：多Master多Slave、DLedger Raft自动选主
  6. 消息轨迹：全链路可查，排查丢消息利器
  7. 选型再确认：事务+延迟+顺序 → RocketMQ 三杀，这是它对比 Kafka/RabbitMQ 的核心卖点
