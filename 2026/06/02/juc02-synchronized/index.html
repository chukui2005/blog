4.1 偏向锁：一段优化史

思路：大多数情况下锁总是由同一个线程获取，那就干脆把这个线程 ID 记在对象头上，下次它再来，比对一下 ID 就放行，连 CAS 都省了。

重要更新：偏向锁在 JDK 15 被默认关闭（JEP 374），后续版本被废弃。原因是：撤销成本高、维护复杂，而现代应用里锁竞争比想象中多，收益不明显。

面试如果被问”偏向锁现在还用吗”，能说出这一点，是明显加分。

4.2 轻量级锁：自旋 CAS

适合的场景：竞争时间极短（比如加锁代码只有几行）。自旋的时候线程还在跑（消耗 CPU 但不做上下文切换），比挂起唤醒划算。

自旋次数是自适应的（-XX:+UseSpinning 默认开，JDK7 后由 JVM 自己调）。

一句话记：偏向锁解决”只有一个线程”，轻量级锁解决”竞争但不激烈”，重量级锁解决”竞争激烈”。

六、synchronized 和 Lock 怎么选

维度 synchronized ReentrantLock
实现层面 JVM 关键字（monitorenter） JDK 类（AQS）
锁释放 自动（异常也释放） 必须 finally 手动 unlock
可中断 不支持 lockInterruptibly()
超时 不支持 tryLock(timeout)
公平锁 非公平 可选公平/非公平
条件变量 一个（wait/notify） 多个（newCondition）
性能 JDK6 后优化后接近 差不多

结论很简单：能用 synchronized 就用 synchronized，需要超时、可中断、多条件队列、公平锁的时候才用 Lock。
