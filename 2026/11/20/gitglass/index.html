我写了一个开源 Git 客户端：GitGlass —— 每一次改动，先看清再提交

我写了一个开源 Git 客户端：GitGlass

👉 GitHub 地址

这是什么东西

一句话：一个本地优先的桌面 Git 工作台，界面上想做成 dbx 那种感觉。

用起来是这样的：选中要提交的文件，看真实的 git diff，确认没问题再暂存、再提交。所有操作背后执行了什么命令、在哪个目录执行、输出是什么、退出码是多少，都能在「命令账本」里翻出来。

为什么又造一个 Git 客户端

起因很具体。

命令行 git 我天天用，但它有两个问题：一是看不见，git reset --hard、git rebase、git push -f 这些命令一旦手滑，代价是很实在的；二是记不住，隔几天不用就得回去翻 git reflog 那套救命流程。

后来我也试过几个图形客户端，但用着用着总觉得别扭：它们大多把 git 命令藏在按钮后面，点下去发生了什么你不知道；出了问题想去对一下实际执行的命令，只能靠猜。而且不少工具越来越重，打开一个本地仓库要等它同步、拉取、加载一堆用不上的东西。

我想要的东西其实很简单：

  • 一切可见：操作背后到底跑了哪条命令，得能看见
  • 危险操作必须拦住：不能悄悄执行 force push、reset --hard、rebase
  • 本地优先：只用我机器上装好的 git，不要上传任何仓库内容
  • 界面要顺眼：这条是硬需求，天天开的东西，丑了真的用不下去

于是就有了 GitGlass。11 月 11 日开始写，现在到 0.6.8。

界面：参考了 dbx 的设计

界面这件事我得坦白说：UI 风格是照着 dbx 做的。

侧边栏放导航，主区域是内容，信息密度刚好，不堆按钮，少用颜色，靠层级和留白来组织信息。暗色模式也是同一套逻辑，而不是简单反色。

为什么照它做？因为 dbx 是我今年见过最舒服的桌面工具界面——克制、干净，任何一屏你知道该看哪儿。数据库客户端和 Git 客户端虽然干的活不一样（一个管数据，一个管改动），但都是「左边一堆对象、右边一大片内容」的结构，这套布局其实是通用的。

用 dbx 用久了会形成一种审美：工具应该退到后面，让你专注在手头的事上。GitGlass 就是按这个思路排的。

核心设计一：命令账本

这是整个项目我最在意的部分。

GitGlass 不内置 Git，也不模拟 Git，它调用你机器上装好的 git，每一条实际执行的命令都记在账本里：

  • 准确的 argv（到底是 git add -A 还是 git add src/foo.ts，一目了然）
  • 工作目录
  • stdout / stderr
  • 退出码
  • 操作来源：是你点的，还是系统后台读取状态触发的

平时折叠成一行结论，需要排查的时候再展开看技术输出，还能直接把命令和诊断信息复制出来。

这个东西的价值在于：图形界面不再是黑盒。 你点了什么，它跑了什么，成功还是失败，全都能对上。出了问题不用再靠猜，也不存在”GUI 偷偷替我做了个 merge”这种事。

核心设计二：安全边界

GitGlass 的原则是「计划 → 确认 → 再校验」，有风险的动作不会自动往下走。

具体做了这些：

  • Fetch / Push / pull --ff-only 都会先给你看计划，确认了才执行
  • 丢弃改动：只支持单个已跟踪、未暂存的文件，而且必须先看过 diff、再输入文件名确认，才会丢掉
  • 删除分支：只允许删除已合并、且不是当前的本地分支
  • 直接不支持：force push、删除远程分支、自动 merge、rebase、stash、reset --hard 全都不做

有人会问，这些功能都不支持，那算什么 Git 客户端？

我的想法是：故意不做。 这些操作的破坏性太强，用命令行做的时候你至少是明确知道自己在下狠手；放到图形界面里一个按钮搞定，反而危险。GitGlass 的定位是「日常提交和审阅」，狠活请回命令行。

代价当然有，但换来的是：在这个工具里，点错按钮几乎不会造成不可逆的损失。

核心设计三：历史是用来审阅的

大多数客户端的历史面板其实只是「列表」。GitGlass 希望它能用来审阅：

  • 看近期提交、统计、改动文件和完整 diff
  • 两个提交之间做比较，方向固定为「基准 → 对比」，不会搞反
  • 按关键词、作者、本地分支、已跟踪文件筛选历史
  • 跟踪单个文件的历史
  • 所有筛选和查看都不改变工作区——看历史就只是看历史

还有一个我很喜欢的恢复设计：从 reflog 条目创建救援分支。 reset 撤错了、rebase 搞丢了提交，不用记那些命令，直接从 reflog 里挑一条把分支捞回来。

技术栈

不复杂，都是常见的东西：

  • Electron + React + TypeScript + Vite：桌面应用外壳和界面
  • Phosphor Icons：图标库，风格统一
  • electron-updater：自动更新
  • Vitest + Testing Library：单元测试和组件测试
  • ESLint：代码规范

架构上最核心的一条是：所有 Git 操作都走真实命令，不碰 .git 内部结构。 好处是行为和你手敲命令完全一致，坏处是每次操作都要管进程、解析输出、处理退出码——所以才有命令账本，因为它本来就得记。

另外 GitGlass 不收集、不上传、不托管任何仓库内容，纯本地跑。

现在的限制（先说清楚）

  • 目前只支持 Windows x64，需要机器上装了 Git，且命令行能直接用 git
  • 安装包还没做代码签名，Windows SmartScreen 可能会提示「未知发布者」
  • 不支持 force push、删除远程分支、自动 merge、rebase、stash、reset --hard
  • 版本号还是 0.x，功能边界还会调

这些不是”以后再说”的托词，是当前的实际情况，写在 README 里了。

想试试的话

Windows 用户可以直接下最新稳定版，有 NSIS 安装包和便携 ZIP 两种：

👉 https://github.com/chukui2005/GitGlass/releases/latest

项目 Apache-2.0 开源，代码在 https://github.com/chukui2005/GitGlass ，欢迎提 issue 和 PR。

最后

写这个项目最大的收获，是想清楚了一件事：工具的边界感和透明度，比功能数量重要。

一个 Git 客户端可以支持一百个功能，但如果它让你不知道自己在干什么，那它就是在给你制造风险。GitGlass 选择反过来做——把每一条命令摊开给你看，把危险的东西直接拒之门外，剩下的部分做干净、做顺手。

界面学 dbx，安全性学命令行，大概就是它的性格。
