二、事务传播行为（7种）

传播行为定义了调用方和被调用方之间的事务边界。

2.1 REQUIRED（默认）

2.2 REQUIRES_NEW（新建事务）

应用场景：操作日志记录——日志失败不能影响主业务。

2.3 NESTED（嵌套事务）

NESTED vs REQUIRES_NEW：

  • REQUIRES_NEW：完全独立，外层异常不影响内层（已提交）
  • NESTED：依赖于外层事务，回滚到 savepoint，外层可控制最终提交

2.4 传播行为汇总

传播行为 外层有事务 外层无事务
REQUIRED（默认） 加入外层事务 新建事务
REQUIRES_NEW 挂起外层，建新事务 新建事务
NESTED 外层事务中建 savepoint 新建事务
SUPPORTS 加入外层事务 非事务执行
MANDATORY 加入外层事务 抛异常
NOT_SUPPORTED 挂起外层，非事务执行 非事务执行
NEVER 抛异常 非事务执行

三、隔离级别

3.1 @Transactional 隔离级别

隔离级别 脏读 不可重复读 幻读
READ_UNCOMMITTED ✅ ✅ ✅
READ_COMMITTED（默认） ❌ ✅ ✅
REPEATABLE_READ ❌ ❌ ✅
SERIALIZABLE ❌ ❌ ❌

MySQL InnoDB 默认 RR，但 Spring 的默认隔离级别是“使用数据库默认”（DEFAULT），所以 Spring + MySQL 组合实际是 RR。

3.2 readOnly 优化

readOnly 的作用：

  • 底层 JDBC 驱动会做优化（如 MySQL 跳过排他锁）
  • JPA/Hibernate 会跳过 flush 脏检查
  • 明确语义——告诉团队这个方法不会写数据

四、事务失效的 5 种场景（面试最高频）

场景 1：异常被 catch 吞掉

解决： catch 时不处理就重新抛出去，或者手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()。

场景 2：检查异常（Checked Exception）

解决： 配置 rollbackFor。

场景 3：方法不是 public

原因： Spring AOP 基于代理，只能拦截 public 方法。

场景 4：同类内部方法调用

解决： 注入自身代理，或者拆到另一个 Service。

或者用 @EnableAspectJAutoProxy(exposeProxy = true)：

场景 5：事务传播行为配置不当

解决： 每条记录独立事务，用 REQUIRES_NEW。

七、面试高频题

Q1：@Transactional 加在接口上还是实现类上？

加在实现类上。 因为：

  • 加在接口上，只有 JDK 动态代理生效，CGLIB 不识别
  • Spring 官方也推荐加在实现类上

Q2：大事务怎么优化？

大事务问题：长事务持有数据库连接，锁资源久，容易死锁。

Q3：@Transactional(readOnly=true) 真的不开启事务吗？

不是。 它依然会开启事务，只是设置事务为只读模式。底层数据库可能有优化（如 MySQL 的 InnoDB 只读事务可以跳过某些锁）。
