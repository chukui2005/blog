DeepSeek Harness：Agent = 模型 + 工程底座

核心知识点速览

知识点 要点
是什么 DeepSeek 官方开源的 agent harness，命令行叫 dsh，MIT 协议
发布时间 2026-08-13，v0.1 开发者预览，和 DeepSeek-V4-Pro 同期
核心口号 Everything is a Plugin（一切皆插件）
底层框架 Cordis —— 插件贡献服务、类型化事件、可撤销副作用
关键理念 Agent = Model + Harness，模型负责想，harness 负责在受控环境里执行
运行形态 Web UI（默认 3080）/ 桌面端 / headless / SDK / ACP
上手成本 npx @deepseek-ai/dsh web 一条命令
现状 迭代极快，官方明说会有破坏性变更，别直接上生产

一、先讲清楚 Harness 是什么

1.1 一个公式

很多人以为”做个 AI 编程助手”就是接个大模型 + 写个好提示词。实际完全不是。

一个能干活的 agent，模型之外还需要一整套东西：

  • 系统提示词怎么拼、什么时候更新
  • 工具怎么注册、参数 schema 怎么进上下文
  • 会话状态怎么存、断了能不能续
  • 命令在哪执行、要不要沙箱、危险操作要不要人工确认
  • 上下文超了怎么压缩、失败重试几次、子 agent 怎么调度
  • 出了事怎么回放、怎么定位是哪一步出的问题

这些加起来才是 harness。Claude Code、Codex、Cursor 的 agent 模式，本质上都是 harness 工程的产品形态。

1.2 dsh 和它们有什么不一样

一句话区别：

官方给的定位很明确：不是又一个编程助手，而是想让开发者自己拼出自己的 agent。

这个选择很聪明——今天最优的 agent 循环、工具协议、记忆方案，明天可能就被推翻。与其赌一个正确答案，不如把零件标准化，让人换得起。

二、一切皆插件，到底”一切”到什么程度

打开它的架构文档，第一句话就很硬：

Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself.

翻译一下：模型适配器、工具注册表、会话日志、甚至 agent 主循环本身，都是插件。

而且：

There is no privileged core to patch.

没有需要你打补丁的特权内核。你要扩展 dsh，就是在旁边挂一个插件；插件的注册是一种”副作用”，插件卸载时这些注册会自己撤销（reversible effects）。

这带来几个很实际的好处：

  • 换模型不用改业务：模型适配器是插件，DeepSeek 只是默认选项
  • 能力可裁剪：不需要的能力不挂载，进程里就不存在那段代码
  • **能测出”能力到底来自哪”**：同一套会话、工具、权限，只换模型适配器，跑分差异就是模型的锅；反过来，同模型换 harness，差异就是工程的价值

最后这点其实挺重要。行业里一直有个说不清的问题：一个 agent 表现好，到底是模型强，还是提示词和工具编排得好？dsh 这种解耦设计，让这个问题至少变得可实验。

三、架构拆解：插件树是怎么长出来的

3.1 Cordis 打底

dsh 的底座是 Cordis（Koishi 生态同款），设计思想写在论文《A Programming Paradigm for Spatiotemporal Composability》里。

你可以把它理解成一个”带生命周期的依赖注入容器”：

所以 dsh 里到处是 ctx.xxx：

包 负责什么 挂在哪个 ctx 上
core/session 只追加的会话事件日志 + 内存存储 ctx.sessions
core/system-prompt 提示词片段与工具 schema 的组装 ctx.systemPrompt
core/tools 作用域内的工具注册表 + 带守卫的执行管线 ctx.tools
core/agent Agent 接口、活体注册表、agent/* 事件 ctx.agents
core/agent-loop 默认驱动器，实现 agent 循环 ctx.agentLoop
llm/llm 消息与流式协议、适配器接缝 ctx.llm

3.2 Profile 和 Bundle：配置即组合

dsh 启动时不是”加载一个大程序”，而是按顺序叠加若干层配置，最终长出一棵插件树。

官方自带几个 profile 模板：

  • web —— 浏览器 UI（默认就是这个）
  • headless —— 无服务器的一次性执行器，适合跑 CI
  • sdk / sdk-minimal —— 给 SDK 用的 JSON-RPC 服务
  • acp —— 只给自动化用的 ACP 服务

dsh-base 是 web / headless / sdk / acp 共享的第一层，里面放着模型适配器、工具、持久化、沙箱与审批策略、设置、凭证、遥测。再往上，dsh-web-app 加浏览器应用，dsh-headless 加一次性执行，各管各的。

四、会话日志：整个系统的地基

如果要我只挑一个设计说，那就是这个。

4.1 Model-visible means logged

架构文档里有一句很关键的话：

Model-visible means logged. Every model request must be reconstructable from the log.

模型能看到的任何东西，都必须能从日志里重建。这条约束推导出整个设计：

好处非常明显：

  • 可回放：系统提示词、思维链、工具调用、子 agent 调度，全在日志里
  • 可分叉：在某个 turn 边界 fork 出一条新分支，试不同方案，不影响主线
  • 可迁移：日志有版本号（session.vN.jsonl），格式升级走逐版本迁移链，旧会话仍然能打开
  • 可审计：出了线上事故，能精确还原”当时模型看到的是什么”

对比一下大多数 agent 实现：会话状态是内存里的一堆对象，持久化时随便序列化，恢复时字段对不上就丢一半。dsh 是反过来——日志是唯一真相，其他都是投影。

4.2 Turn 和 Step

它的主循环抽象得很干净：

区分 turn 和 step 很关键：一个 turn 里模型可以连续跑多个工具调用，而不是一问一答。用户说的”帮我修好这个 bug”，在 harness 里是一个 turn，可能包含七八个 step。

4.3 三类事件

它的扩展点分成三个域，别搞混：

类型 特点 什么时候用
Session events 落到日志里，重载后还在 这个事实必须持久
Agent events（agent/*） 携带活的 Agent 对象 观察或拦截飞行中的工作
Capability events（fs/*、tools/*） 把策略和适配器接到接缝上 加策略，但不碰循环

五、Capability Seam：换一个 provider，换一整个执行世界

这是我觉得最有工程味的设计。

一个 seam（接缝） 由三个角色组成：

文档里举的例子很到位：

文件系统和子进程这两个 provider 共享同一个执行世界。把它们指向远程沙箱，Bash、PTY、LSP 就跟着一起搬过去了，不用 fork 任何 provider。

什么意思？

对比那些”在工具里硬编码 child_process.spawn“的实现，这种设计的差别是：隔离性是配置项，不是重写量。

同理，ctx.sandbox 管进程隔离、ctx.tools 管工具执行管线、ctx.agents 管子 agent 调度，每个都是一个可替换的接缝。

文档甚至给了张”新行为该往哪放”的表，我摘几条：

你想干什么 挂到哪里
加一个模型厂商 在 ctx.llm 注册适配器
加一个给模型用的能力 在 ctx.tools 注册，schema 自动进提示词
加 shell 执行后端 注册 ctx.shell，本地实现走 ctx.subprocess
拦截一次请求 / 工具 / turn 监听对应事件，agent/turn-stopping 能停整个 turn
加模型可见的上下文 agent.inject()，落到下一次请求

扩展点是被文档化的，不是”你自己去翻源码找 hook”。这点对想二次开发的人很友好。

六、跑起来

6.1 最快路径

默认在 http://127.0.0.1:3080 起 Web UI，并自动打开浏览器。加 --no-open 就只起服务不弹窗（SSH 场景下默认也不会乱开）。

6.2 从源码跑

开发时用 pnpm run dev:web，改客户端代码会边构建边热更新。

6.3 五种运行形态

Profile 场景
web 本地浏览器 UI，日常用
headless 无服务器一次性执行，塞进 CI/脚本
sdk / sdk-minimal 给 SDK 调，JSON-RPC 暴露 agent
acp 纯自动化 ACP 服务
桌面端 Electron 应用，内置同一套运行时

形态不同，但用的是同一套插件树和配置——桌面端和 npm CLI 共享产品数据，但包、激活、锁文件分开管理。

6.4 模型可以换

DeepSeek 只是默认。模型适配器是插件，官方文档里给的 provider 包括 DeepSeek、Anthropic、OpenAI，以及 Kimi（Moonshot）、GLM（Z.AI）这些，也支持自定义 endpoint。

API key 在设置里填，界面上是只写的；实际存在 $DSH_HOME/.credentials.yaml，设置里只保留引用。这种处理还算规范。

不吹不黑，三个维度：

所以选型建议很简单：

  • 只想提效写代码 → 用成熟产品，别折腾

  • 企业内要做 agent 平台 → 它的 seam 设计、日志模型、配置分层，是可以直接借的参考答案

八、几个值得抄的设计

抛开”用不用”，这套架构里有几个思路我觉得做后端的人也值得看一眼：

1. 只追加日志 + 投影
会话状态不是”存一份对象”，而是”记一串事实，需要什么就投影什么”。这就是事件溯源（Event Sourcing）在 agent 场景的落地。日志版本迁移那条链，也是标准的 schema 演进套路。

2. 可撤销的注册
插件注册的东西在卸载时会自动回滚，不需要手写 cleanup。这是”资源生命周期跟作用域绑定”的老思想，但用在插件系统里收益很大——热插拔才真的可行。

3. 分层 patch，而不是 fork 配置
默认配置 → profile → 用户 patch → 命令行覆盖。每层只写差异，排障时 --dump-config 一看就知道最终生效的是什么。这个模式在任何”可配置中间件”里都成立。

4. 接缝三件套
定义、实现、使用方分离，且换实现不改使用方。写 Java 的应该很熟——这就是 SPI 的思路，只不过它把”哪些能力必须做成 SPI”想清楚了。

九、注意点

  • 别上生产。v0.1 开发者预览，AGENTS/架构都在动，破坏性变更明说了
  • 先读 SAFETY.md。它能执行 shell、读写文件，harness 层有沙箱和审批策略，但默认配置不一定适合你
  • star 涨得快 ≠ 可以直接依赖。这类项目看架构比看 star 有用
  • 文档质量高于预期。架构文档、能力接缝图、扩展 cookbook 都有，这在开发者预览阶段挺少见

小结

DeepSeek Harness 最值钱的不是”又一个能写代码的 agent”，而是它把 harness 工程这件事拆开摆在了台面上：

模型是变量，harness 是工程；模型会换，harness 的设计会沉淀。

如果之前用过 Claude Code 只觉得”神奇”，那读一遍 dsh 的架构文档，大概就能明白那份”神奇”是怎么被工程化出来的——提示词组装、工具管线、会话日志、沙箱审批、循环控制，一层都不能少。

想动手的话，npx @deepseek-ai/dsh web 就够了，五分钟能跑起来；想看懂的话，docs/architecture.md 值得花一个晚上。
