PostgreSQL：为什么越来越多的团队在用 PG

核心知识点速览

知识点 要点
PG是什么 开源对象关系型数据库，功能最全的通用数据库之一
进程模型 一个连接一个后端进程（fork），非线程模型
MVCC实现 堆表多版本 + xmin/xmax，旧版本靠 VACUUM 回收（无 undo log）
默认隔离级别 Read Committed（MySQL 默认 RR）
索引类型 B-tree（默认）/ Hash / GIN / GiST / BRIN / SP-GiST
高可用 WAL 物理流复制 + 逻辑复制 + PITR
特色能力 JSONB、数组、Range、全文检索、扩展生态、DDL 事务
应用场景 复杂查询、强一致业务、地理信息、混合负载、AI 应用后端

一、先搞清楚 PG 在解决什么问题

1.1 它和 MySQL 的定位差异

国内这两年 PG 的声量明显变大，原因大概几个：

  • 授权问题：MySQL 属于 Oracle，很多公司出于合规考虑在迁
  • 复杂查询：窗口函数、CTE、JSONB、GIS、全文检索，PG 原生能力更完整
  • 扩展生态：TimescaleDB（时序）、PostGIS（地理）、pgvector（向量），一个库 cover 多种场景
  • 厂商支持：华为 GaussDB、阿里 PolarDB-PG、腾讯 TBase 都是 PG 系

1.2 PG 的进程模型

这是理解 PG 的第一个关键点，和 MySQL 完全不同。

所以面试问「PG 支持多少并发」，正确回答不是给个数字，而是：单机建议几百以内直连，更高并发上 PgBouncer 做连接池，事务级池化模式最常用。

二、MVCC：PG 最核心的机制

2.1 堆表多版本

PG 的 MVCC 是追加式的：更新不是原地改，而是写一条新版本的行。

对比 MySQL：InnoDB 是原地更新 + undo log，旧版本通过回滚段重建；PG 是新版本直接留在表里，旧版本要等清理。

2.2 代价：表膨胀与 VACUUM

因为是追加写，PG 的表会越来越”胖”：

几个必须知道的点：

  • VACUUM 只是标记空间可复用，不还给操作系统；VACUUM FULL 才重写整表（会持排他锁，生产慎用）
  • 长事务是性能杀手：它会让 autovacuum 清不掉更晚的死元组，导致表膨胀
  • 事务ID是 32 位循环的，长期不 freeze 会触发 wraparound 保护，实例会强制停写

2.3 隔离级别

面试常问的坑：PG 的 RR 不会出现幻读，因为整个事务用同一个快照；但它不是靠间隙锁实现的，所以也不会像 MySQL 那样出现死锁型的幻读问题，代价是可能在 Serializable 下抛 could not serialize access due to concurrent update，业务需要重试。

三、索引：PG 的索引家族比 MySQL 丰富得多

3.1 默认是 B-tree，但不是唯一选择

索引类型 适用场景 典型例子
B-tree 等值、范围、排序 主键、时间字段、普通业务字段
Hash 纯等值查询 枚举值、ID 精确匹配
GIN 多值类型（数组、JSONB、全文） jsonb @> '{}'、tsvector @@
GiST 几何、范围、相似性 PostGIS、daterange 重叠判断
BRIN 超大表、物理有序 时序数据按时间插入
SP-GiST 空间分区树 电话号码、IP 段

3.2 几个高级玩法

3.3 没有聚簇索引这件事

MySQL InnoDB 是聚簇索引：主键 B+ 树叶子节点直接存整行，二级索引查完要回表。

PG 是堆表 + 独立索引：所有索引叶子节点存的都是 ctid（物理位置），查完都要回表。

HOT（Heap-Only Tuple）是 PG 的一个优化：更新时如果没有修改任何索引列，且新版本能放进同一页面，就不新增索引项，只更新链指针——这也是为什么「不要随便给高频更新的列建索引」。

小结

PG 的学习曲线比 MySQL 陡一点，主要在进程模型、MVCC 的清理机制、索引家族这三块。

但一旦理解了「堆表 + 多版本 + VACUUM」这条主线，很多东西就串起来了：为什么长事务危险、为什么要盯表膨胀、为什么覆盖索引重要、为什么 BRIN 在时序场景下这么香。

对 Java 后端来说，MySQL 依然是主力，但 PG 的能力边界更宽——尤其是需要 JSONB 做半结构化存储、需要 pgvector 做检索、需要 PostGIS 做位置服务的时候，一个库就能省掉一套中间件。
