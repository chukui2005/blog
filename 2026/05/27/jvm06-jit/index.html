一、Java 为什么”编译 + 解释”两条腿走路

为什么不直接全部编译成机器码（像 C++）？

这也解释了一个现象：Java 服务刚启动时慢，跑一会儿就快了——预热（warm up）说的就是这个。

Spring Boot 启动慢、压测第一分钟 TPS 明显低，都是这个原因。

二、热点探测：哪些代码值得编译

JVM 不会把”编译过的方法”再编译一遍，也不会编译只跑过一次的方法。判断标准是”热度”。

2.1 基于采样的热点探测

定期看线程栈顶，某个方法经常出现在栈顶，就是热点方法。

  • 优点：简单，能发现”一个方法里嵌了很多小方法”的整体热点
  • 缺点：不精确，受线程阻塞影响

2.2 基于计数器的热点探测（HotSpot 采用）

OSR 很关键：一个方法里有死循环，方法本身只调用了一次，但循环跑了几万次——这时候 JVM 不会等你方法执行完再编译，而是直接把正在执行的循环替换成编译后的版本。

计数器还有”热度衰减”：一段时间内没被调用，计数会减半（-XX:-UseCounterDecay 可关闭），避免以前的冷代码一直占着编译队列。

3.1 分层编译（JDK7 后默认）

典型路径：0 → 3 → 4（先 C1 带 profiling 跑着，同时后台让 C2 慢慢编译高质量版本）。

分层编译的收益：启动阶段用 C1 快速提供中等性能，运行稳定后 C2 接管提供峰值性能——两头的好处都要了。

4.2 逃逸分析后能做三件事

① 栈上分配

如果对象不逃逸，完全可以分配在栈上，方法返回时随栈帧一起销毁，不用 GC 收拾。

注意一个常见误区：HotSpot 实际上**没有真正实现”栈上分配”**，它用的是标量替换达到类似效果。面试如果被追问，能说出这点是加分项。

② 标量替换（Scalar Replacement）

对象根本没被创建，自然没有分配和 GC 开销。

③ 锁消除（Lock Elision）

如果对象不逃逸，那么对它的同步就毫无意义，直接干掉：

这就是为什么”用 StringBuffer 一定比 StringBuilder 慢”不一定成立——单线程短生命周期场景，JIT 会把锁去掉。

五、其他常见优化

5.1 方法内联

最基础也最有效的优化：把小方法的代码直接贴到调用处，省掉调用开销，还能为后续优化打开空间。

内联之后，常量折叠、死代码消除才有机会生效。所以getter/setter 这类小方法不用担心性能，JIT 会处理。

内联也有副作用：CodeCache 会膨胀，方法太大内联失败。

5.2 去虚拟化

单态调用（只有一个实现）最容易优化，多态（多个实现）就得退回查虚表。

六、逆优化（Deoptimization）

C2 的激进优化是基于假设的：

一旦假设被打破（比如热更新加载了新的实现类），JVM 会把这段代码退回解释执行，重新收集信息再编译。这个过程叫逆优化。

线上如果出现”偶发的性能抖动 + 逆优化次数暴涨”，通常是类加载导致的类型假设失效——比如动态代理、热部署、Groovy 脚本频繁生成新类。
