我写了一个开源组件：OpenAI Code Review

👉 GitHub 开源地址

这是什么东西？

一个基于 DeepSeek API 的自动化代码评审组件，跑在 GitHub Actions 上。

流程很简单：你往仓库推代码 → Action 自动触发 → SDK 拉出本次的 git diff → 发给 DeepSeek 评审 → 结果存到一个专门的日志仓库里 → 可选通过微信模板消息通知你。

为什么要写它？

之前面了不少公司，发现很多团队对代码评审这件事执行得很敷衍 — 要么没时间做，要么做成了走过场。但代码评审其实是提升质量的硬道理。

我的想法是：把评审这件事自动化。每次 push 自动跑一次，不费人力，而且 AI 不会漏看细节。

遇到的难点

1. git diff 的获取

第一版想用 JGit 的 API 直接拿 diff，结果发现 JGit 的 DiffFormatter 在 GitHub Actions 环境里行为不太一样。后来换成了 ProcessBuilder 调原生 git 命令，反而更稳。

但这里有个坑：git log -1 拿到的是最新 commit hash，但首次 push 时 parent 可能不存在（第一个提交），会导致 diff 失败。需要确保 fetch-depth: 2 来拿到父 commit。

2. JGit 的认证问题

把评审结果 push 到日志仓库时用了 JGit。JGit 的认证方式和原生 git 不太一样，必须用 UsernamePasswordCredentialsProvider，而且用户名固定写 "token"，密码才是真正的 GitHub Token。这个在文档里不明显，踩了坑。

3. 微信模板消息的集成

微信模板消息的流程比较啰嗦：先拿 access_token（有效期 2 小时），再用 token 发模板消息。而且模板里的变量名必须和公众号后台定义的一模一样，少一个冒号都报错。

为了区分必填和可选配置，我在代码里做了特殊处理：只有配了 WEIXIN_APPID 才初始化微信客户端，其他三个微信参数自然也变成必填了。这个取舍想过几种方案，最后还是觉得「明确告诉用户这是可选的」最直接。

4. 多模块的构建发布

SDK 需要打成可执行 JAR 发布到 GitHub Releases，用户通过 curl 下载。这就需要在 GitHub Actions 里先 mvn package，再用 softprops/action-gh-release 上传 artifact。

但多模块工程的依赖关系要注意：test 模块依赖 sdk 模块，打包时如果不先 install sdk，test 模块会编译失败。解决方案是用 mvn -DskipTests clean install 先装到本地仓库。

5. 环境变量的设计哲学

SDK 启动时从环境变量读取配置。我设计了两套读取方式：

  • getEnv() — 必须存在，没有就抛异常（CODE_TOKEN、DEEPSEEK_API_KEY 等）
  • getEnvOptional() — 可选，没有返回 null

这看起来简单，但一开始我把所有变量都搞成必填了，用户少配一个微信就崩。后来才改成微信相关全部 optional，代码里判断 null 跳过。

一些小想法

写这个组件最大的收获不是学会了 JGit 或者微信 API，而是理解了怎么让一个工具真正「好用」：

  1. 模板要可复制 — 用户拿来改两行就能用，而不是从零写起
  2. 报错要明确 — 缺了哪个配置、哪里填错了，日志要一眼看出来
  3. 可选功能别强求 — 微信通知很酷，但不是每个人都需要，别让人家因为不想配微信就用不了
