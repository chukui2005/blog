Docker：镜像、容器与生产部署实践

核心知识点速览

知识点 要点
容器是什么 被 namespace 隔离、被 cgroups 限制的普通进程
镜像 只读的分层文件系统，容器启动时叠加一层可写层
分层机制 每层只记录与上层的差异，层可复用，构建缓存的关键
网络 bridge（默认）/ host / none / container，自定义网络才有 DNS
存储 volume（Docker 管理）/ bind mount（宿主机路径）/ tmpfs
构建优化 多阶段构建、.dockerignore、合并 RUN、利用缓存顺序
JVM 适配 Java 10+ 支持容器内存感知，配 -XX:MaxRAMPercentage
与 K8s 关系 Docker 是单机容器运行时，K8s 是跨机编排

一、容器到底是个什么东西

1.1 一句话本质

所以在容器里 ps aux 只能看到自己的进程，top 看到的内存是被限制后的值——这些都是隔离和限额的结果，不是虚拟化。

1.2 和虚拟机的区别

维度 虚拟机 容器
隔离级别 硬件虚拟化，独立内核 进程级隔离，共享宿主内核
启动速度 几十秒 毫秒到秒
资源开销 每台都跑完整 OS 几乎只有应用本身
隔离强度 强（内核都独立） 较弱（内核共享，逃逸风险更高）
镜像体积 GB 级 MB 级

结论：容器不是用来替代虚拟机的，是用来替代”手动配环境”的。

二、镜像：分层是理解一切的基础

2.1 镜像怎么存

这个设计带来两个直接后果：

  • 层可以复用：10 个基于 eclipse-temurin:17-jre 的镜像，宿主机上只存一份基础层
  • 构建缓存有顺序：Dockerfile 里改动越靠后的指令，越不会让前面的缓存失效

2.2 为什么 COPY 的顺序很重要

COPY / RUN 的缓存判断依据是输入内容有没有变。所以把变化频率低的东西放前面，是压缩构建时间的核心技巧。

2.3 多阶段构建：把编译环境和运行环境分开

效果很直接：几百 MB 的 Maven 和 JDK 全部留在 builder 阶段，最终镜像只剩 JRE + jar，通常 150 MB 以内。

3.1 状态流转

关键点：容器的生命周期绑定主进程（PID 1）。主进程退出，容器就退出。

所以 ENTRYPOINT 不能写成 service nginx start 这种后台启动脚本——脚本一退出容器就死了。正确写法是前台运行 nginx -g 'daemon off;'。

四、网络：容器之间怎么通信

4.1 五种网络模式

模式 说明 使用场景
bridge 默认，通过 docker0 网桥 NAT 出网 单机普通容器
host 直接用宿主机网络栈，没有独立 IP 高性能场景，端口冲突要自己管
none 只有 lo，无网络 纯计算任务
container 共享另一个容器的网络命名空间 sidecar 场景
自定义 bridge 用户自己创建的网络，带 DNS 多容器协作，推荐

4.2 最容易踩的坑：容器名解析

所以在 compose 里写 jdbc:mysql://mysql:3306/db，前提是这些服务在同一个自定义网络里。compose 默认会创建一个。

4.3 端口映射的两种写法

顺带一提：EXPOSE 8080 只是元数据声明，不会真的开放端口，端口映射必须靠 -p。

五、存储：数据不能跟着容器一起死

5.1 三种挂载方式

选型原则：

  • 数据库数据、上传文件 → volume
  • 配置文件、开发时挂代码 → bind mount
  • 临时缓存、密钥 → tmpfs

5.2 一个常被忽略的点

容器删除时，volume 不会自动删除（除非 docker rm -v 或 compose down -v）。这是保护数据的设计，但也意味着磁盘会被悄悄占满：

7.1 内存限制不生效的老问题

小结

Docker 的知识点看起来很碎，其实都能挂到三条主线上：

  1. 镜像分层 → 决定构建速度和镜像体积
  2. namespace + cgroups → 决定隔离边界和资源限制（也是 JVM 适配的根源）
  3. 网络 + 存储 → 决定多容器怎么协作、数据怎么活得比容器久

把这三条想清楚，剩下的命令都是查文档的事。
