垃圾回收基础：怎么判断对象死了

核心知识点速览

知识点 要点
判断死亡 引用计数（有循环引用问题）vs 可达性分析（JVM 采用）
GC Roots 栈中引用、静态变量、常量、JNI 引用、活跃线程等
引用类型 强 / 软 / 弱 / 虚，对应不同回收时机
回收算法 标记-清除、复制、标记-整理、分代收集
跨代引用 卡表 + 记忆集，避免 Minor GC 扫全堆
三色标记 白灰黑，漏标的两个条件，增量更新 vs SATB
STW 安全点、安全区域、主动式中断

一、怎么判断一个对象该被回收

1.1 引用计数：简单但有致命缺陷

所以 JVM 没有采用引用计数。Python、Swift 用这套，但都要额外机制处理循环引用。

1.2 可达性分析：JVM 的做法

从一组叫 GC Roots 的对象出发，沿着引用链往下遍历，能走到的对象是”活的”，走不到的就是垃圾。

1.3 GC Roots 有哪些

这个必须背下来：

  • 虚拟机栈中局部变量表引用的对象（正在执行的方法的入参、局部变量）
  • 方法区中类静态属性引用的对象
  • 方法区中常量引用的对象（字符串常量池里的引用）
  • 本地方法栈中 JNI 引用的对象
  • 活跃线程（Thread 对象本身就是一个 Root）
  • synchronized 持有的对象
  • JVM 内部引用（基本类型对应的 Class 对象、常驻异常对象、系统类加载器）

一句话理解：凡是”正在被使用的”和”全局可达的”，都是 Root。

二、四种引用类型

类型 回收时机 典型用途
强引用 永不回收（除非不可达） Object o = new Object()
软引用 SoftReference 内存不足时回收 缓存（图片、查询结果）
弱引用 WeakReference 下次 GC 就回收 ThreadLocalMap 的 key、WeakHashMap
虚引用 PhantomReference 随时可能被回收，只能感知回收 管理堆外内存（DirectByteBuffer 的 Cleaner）

两个常考点：

  • ThreadLocal 内存泄漏：ThreadLocalMap 的 key 是弱引用，value 是强引用。key 被回收后 value 还在，线程池里线程不销毁就永远清不掉——所以必须 remove()
  • DirectByteBuffer 的回收：靠虚引用 + Cleaner，在对象被回收时触发 free() 释放堆外内存

finalize() 就别用了，执行时机不确定、可能让对象”复活”、拖慢 GC，JDK9 起标记废弃。

三条经验规律（分代假说）：

所以堆分成新生代和老年代，各自用最适合的算法：新生代对象死得快 → 复制算法，只复制少量存活对象；老年代存活率高 → 标记-整理，不浪费空间。

四、跨代引用与卡表

问题来了：Minor GC 只扫新生代，但如果老年代有个对象引用了新生代对象，这个新生代对象就不该被回收——怎么知道老年代有没有引用它？

总不能每次 Minor GC 都扫一遍老年代吧。

解决方案：卡表（Card Table）+ 记忆集（Remembered Set）。

5.2 STW 与安全点

GC 必须在一个”引用关系不再变化”的时刻进行，所以要停掉用户线程，这就是 STW（Stop The World）。

不能随时随地停——得停在安全点（Safepoint）：

  • 方法调用、循环跳转、异常跳转这些位置才会插安全点
  • 线程主动轮询一个标志位，发现要 GC 就自己挂起（主动式中断）

为什么不在每条指令都插？因为安全点太多会严重影响性能。

还有个概念叫安全区域（Safe Region）：线程处于 Sleep/Blocked 状态走不到安全点时，标记自己进入安全区域，这段时间引用关系不变，GC 可以放心跑。

六、一次完整的 GC 是怎么发生的

关于年龄阈值还有个坑：Mark Word 里分代年龄只有 4 个 bit，最大 15，所以 -XX:MaxTenuringThreshold 设再大也没用。

小结

这篇的核心就三件事：

  1. 可达性分析 决定谁是垃圾（GC Roots 要背）
  2. 分代 + 复制/整理 决定怎么回收（背后的分代假说）
  3. 三色标记 + 读写屏障 决定并发标记怎么不出错
